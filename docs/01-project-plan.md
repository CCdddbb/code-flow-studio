# 第一步方案：从草稿箱案例到代码可视化生成器

> 历史设计文档。下文包含目标架构与尚未实现能力，不代表当前支持范围。v0.1.0 实际能力见 [实现说明](05-implementation.md) 与 [交付报告](04-delivery-report.md)。

## 1. 目标与产品定位

建设一个面向研发、评审和业务沟通的代码可视化项目。输入代码后，系统生成解释业务流程与数据变化的页面，而不是只画类图、调用图或输出文字总结。

核心价值：**把代码里的数据处理逻辑，变成可以一步步播放、核对和理解的过程。**

一个合格的输出应能回答：

1. 入口接受什么数据，要求哪些前置条件？
2. 数据经过哪些组件、接口和字段转换？
3. 哪些记录被创建、更新或删除？
4. 状态、版本、幂等键如何变化？
5. 哪些操作处于同一事务，哪些异步执行？
6. 成功、拒绝、失败、未知结果分别如何收尾？
7. 哪些结论有源码证据，哪些只是演示假设，哪些尚未解析？

### 输入形式

- 代码片段：解释片段本身，缺失依赖列为未知，不补写完整业务。
- 本地文件/模块目录：首期主场景；用户选择或确认业务入口。
- 整仓库：后续支持按模块和入口筛选，不一次展开全仓库。

默认本地分析。外部模型分析需显式开启，并说明发送的代码范围。

## 2. 已有成果与差距

已检查作为外部参考的 `draft-review-demo` 的 README、场景配置、数据库流程配置、核心回放逻辑及页面主体。以下是基于这些文件的初步盘点，不是逐行审计或测试验收。

| 已有成果 | 可沉淀能力 | 当前限制 |
| --- | --- | --- |
| `scenario.json` | 场景步骤、规则说明、源码位置 | 人工编写，绑定草稿提交 |
| `db-flow.json`、`failure-flow.json` | 多阶段快照、事务窗口、失败分支 | 数据为配置模拟；不能自动提取 |
| `review-core.js` | 字段 diff、路径回放、记录比较 | 固定 draft/main、表名和步骤索引 |
| `integration-json.js` | 字段到 DTO/存储/实体的转换表达 | 特定表单的映射逻辑 |
| `integration-evidence.json`、导出脚本 | 源码摘录、行号、摘要、陈旧校验思路 | 指定模块与白名单锚点，不是通用解析器 |
| HTML/CSS/播放器 | 逐步播放、可视化装配、源码折叠 | 图形节点及文案绑定草稿业务 |
| Node/浏览器测试 | 差异、边界、交互与源码一致性测试思路 | 不能证明通用生成或 Java 执行正确 |

继承的是表达能力和可信度原则，而不是把所有旧逻辑原样复制。

## 3. MVP 范围

### 首期支持

- Java / Spring 源码模块，单一已选入口。
- 优先识别显式 Controller/Service 调用、DTO 字段、常见持久化操作和事务注解。
- 建立有限调用链；反射、动态代理、配置注入等无法可靠解析时显示未解析边。
- 生成成功场景和至少一个**有代码依据**的拒绝/失败场景。
- 输出源码证据、字段变化、数据存储投影、事务边界与交互回放。
- 允许编辑演示输入，在支持的转换范围内重新生成模拟场景。
- 生成本地静态站点，可导出分析 JSON；离线播放不依赖后端数据库。

### 明确不做

- 不承诺任意语言、任意框架的一键完整理解。
- 不自动启动、编译或执行输入仓库，不安装它的依赖。
- 不连接生产数据库，不把模拟快照当成执行采集。
- 不由模型自由生成并执行任意 JavaScript/SQL。
- 不从一个事务注解直接推导“所有下游都处于同一事务”。
- 不把异常自动解释为已回滚，不把未知数据库结果画成空表。

## 4. 架构：分析、场景、渲染分离

```text
输入选择 / 范围确认
  ↓
安全扫描：文件白名单、大小上限、敏感信息过滤、禁止越界路径
  ↓
静态解析：符号、入口、引用、DTO、调用、持久化和事务线索
  ↓
事实模型 + 证据索引
  ↓
语义归纳：步骤命名、规则解释、场景建议（可选模型辅助）
  ↓
统一分析模型：实体、步骤、数据流、分支、证据、待确认项
  ↓
场景构造：确定性样例、受限转换规则、显式快照操作
  ↓
校验关卡：结构、引用、证据、业务不变量、安全与输出边界
  ↓
通用页面渲染：主题 + 布局 + 播放 + 字段 diff + 源码核对
```

### 关键决策

1. **源码事实与语义推断分层。** 静态分析提供可核对事实；模型负责组织表达，不负责凭空证明行为。
2. **JSON 中间模型是核心资产。** 一个模型可以生成网页、报告或其他展示，页面不能依赖业务硬编码。
3. **模拟是可选独立层。** 无法推导转换时，仍可展示流程与证据，不伪造 before/after。
4. **页面是模板与组件组合。** 自动选择适配布局、色彩与信息密度，不每次生成未经验证的任意页面代码。
5. **结果必须可修订。** 用户可以确认入口、修正推断、补充业务假设；修订保留记录，不覆盖原始事实。

### 推荐技术路线（待最小实验确认）

- 工具链与模型校验：TypeScript / Node.js + JSON Schema（Ajv）。
- 页面：React + Vite；复杂可编辑图使用 React Flow，播放器与数据面板独立组件化。
- Java 解析：先做解析器选型实验，比较 tree-sitter-java 与 JavaParser 的字段、调用和符号解析覆盖度。若选 JavaParser，采用独立只读解析进程；不加载或执行输入工程。
- 布局：优先确定性分层布局；复杂图再评估 ELK。
- 测试：Node/Vitest 单测 + Playwright 浏览器回归。
- 模型适配器：可插拔；先验证无外部模型时的静态事实与人工确认流程。

以上为选型建议，本阶段不安装依赖、不宣称解析能力已实现。

## 5. 页面设计

整体采用“流程剧场 + 数据工作台 + 证据抽屉”，默认中文，避免整屏堆源码。

### 页面骨架

```text
[项目/入口] [源码快照时间] [静态分析 + 模拟标识] [导出]
[分析摘要：已知能力 / 未解析依赖 / 待确认结论]

[流程总览：入口 → 校验 → 转换 → 存储 → 回调/响应]
[播放/暂停] [上一步/下一步] [分支] [速度] [阶段时间线]

[步骤导航]  [当前步骤 / 规则]          [演示输入 / 约束]
            [Before → After / 差异]
            [数据库记录 / 事务边界]

[按需展开：字段血缘 / 源码证据 / 未解析项 / 修订记录]
```

### 自动适配不同代码形态

| 代码形态 | 默认可视化 |
| --- | --- |
| CRUD | 请求 → 校验 → 实体 → 存储 → 响应，突出字段变动 |
| 审批/状态机 | 状态迁移图 + 条件 + 合法/非法转换 |
| 异步任务/Outbox | 泳道 + 事务区块 + 重试/确认窗口 |
| 数据转换 | 字段血缘 + JSON 对照 + 类型变化 |
| 可复用能力接入 | 公共底座 + 可替换业务适配器 |
| 无法归类 | 通用流程图 + 事实摘要；提示待补信息 |

样式可自动设计，但必须服从信息表达：服务用中性色，存储用蓝色，变化用强调色，风险用橙红色；颜色不能是唯一标识。支持亮/暗主题、键盘操作、减少动画和窄屏布局。动画速度是演示节奏，不代表代码性能。

## 6. 演示数据与流程分析

演示数据按 DTO 类型、显式校验、测试夹具和已确认业务规则构造，并标注来源。数据采用稳定种子，便于重复验收。

- 字段映射说明来源字段、目标字段、转换规则及证据。
- 存储区默认展示选定字段投影，不暗示完整表结构。
- 插入、更新、删除、字段 unset 必须使用不同操作表达。
- “没有观察到”不等于“不存在”；未知与空集合分开表示。
- 不支持的计算显示 unknown 或要求确认，不使用猜测值伪装计算结果。
- 用户改输入后重新构造假设场景，不声称改动真实已保存数据。
- 只有显式受支持的纯转换可交互重算，其他变更进入待确认状态。

## 7. 验收：第一条自动生成闭环

选择草稿提交入口作为参考用例；入口和范围可人工确认，步骤、组件与证据应由分析管线产生。人工修订必须记录并计入报告。

验收需满足：

1. 输入模块路径与入口后生成可校验的模型和可打开的页面。
2. 还原受理、冻结、业务提交、跨库完成、幂等返回等关键事实；未解析项明确列出。
3. 正确表达主库事务与 MongoDB 之间的非原子窗口，且不依赖草稿专用页面逻辑。
4. 显示字段 diff 和至少一个有证据的失败/拒绝分支，或明确阻止无法验证的分支生成。
5. 每个宣称为源码事实的关键步骤有有效证据；源码变化能判定证据陈旧。
6. 不把模型推断、模拟数据和动画时长显示成实测结果。
7. 自动输出校验与覆盖报告；不只凭截图验收。
8. 第二个非草稿业务样例仅需替换输入与分析结果，不新增业务硬编码渲染器。

## 8. 风险与应对

- 调用链不完整：限制支持范围、记录未解析依赖、提供确认入口。
- 模型编造：事实证据门禁、推断单独标注、不允许补造 Writer/接口/数据库表。
- 场景爆炸：首期每入口选主路径与少量证据支持分支，其他候选列入报告。
- 源码泄露：默认本地、路径最小化、脱敏；导出源码摘录必须授权。
- 不可信仓库：只读取，不执行其脚本；源码中的指令当作数据，不当作工具命令。
- 界面漂亮但分析错误：优先检查语义与数据不变量，再检查视觉布局。
- 草稿案例过拟合：以第二个独立模块作为 MVP 必过关卡。

## 9. 当前结论

先实现一个小而可信的生成闭环，再扩大语言、框架与场景范围。草稿箱案例负责提供参考答案和回归基线，不应成为所有输入的模板答案。
