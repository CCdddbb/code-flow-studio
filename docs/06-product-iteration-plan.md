# Code Flow Studio 产品迭代计划（v0.1.0 → v1.0）

> 文档状态：v0.2 已完成；v0.3 参考场景实验室及路径对比已本地验收，其余仍为计划
>
> 基线版本：v0.1.0
>
> 更新日期：2026-10-15
>
> 说明：本文保留基于 v0.1.0 的路线。v0.2 第一轮范围、设计、限制和实际测试见[第一轮迭代报告](07-v02-iteration-report.md)。除已勾选项目外，后续能力不代表已实现。

## 1. 迭代目标

Code Flow Studio 已完成“源码输入 → 静态分析 → 数据投影 → 证据核对 → 离线导出”的最小闭环。下一阶段不以继续增加页面装饰为目标，而是把当前工具升级为一个可以用于真实项目理解、技术评审和长期知识沉淀的产品。

到 v1.0，产品应能够回答四类问题：

1. 这段业务从哪个入口开始，经过哪些组件和依赖？
2. 输入字段如何转换，状态和持久化数据如何变化？
3. 哪些结论来自源码，哪些是静态推断、人工确认或模拟数据？
4. 当代码发生变化时，原有流程说明和证据是否仍然有效？

## 2. 产品定位

### 2.1 核心定位

面向研发、架构师和技术评审人员的本地代码流程解释与证据核对工作台。

产品不追求“自动理解任意代码”，而是提供一套可信的解释机制：

- 源码事实必须能够回到文件与行号。
- 静态推断必须显式标记，不冒充运行事实。
- 无法确定的行为保留为未知，不补造成功路径。
- 用户可以确认、修订和保存业务语义，但不能覆盖原始分析证据。

### 2.2 首期目标用户

| 用户 | 核心任务 | 首要价值 |
| --- | --- | --- |
| 接手项目的开发人员 | 快速找到入口、调用关系和字段变化 | 降低阅读陌生代码的时间 |
| 架构师/技术负责人 | 评审事务、依赖、状态和异常边界 | 让架构结论有源码证据 |
| 代码评审人员 | 核对一次改动影响了哪些流程 | 识别遗漏和未知影响 |
| 技术产品经理 | 将复杂实现转化为可沟通流程 | 获得可分享的技术说明 |

业务人员不是 v1.0 的直接操作用户，但可以阅读经过脱敏的业务演示版输出。

### 2.3 非目标

- 不替代 IDE、调试器、APM 或运行时链路追踪。
- 不执行用户源码，不自动连接业务数据库。
- 不承诺一次分析完整覆盖整个大型仓库。
- 不把调用命名、框架注解或模型归纳当作真实运行结果。
- 不在缺少授权时对外发送或公开用户源码。

## 3. 当前基线与关键差距

### 3.1 v0.1.0 已具备

- Java、JavaScript、TypeScript 文件导入和本地分析。
- 入口选择与有限静态调用展开。
- 输入契约、字段映射、Before/After 投影与源码证据。
- 未解析连接、分析限制和模拟数据的显式标记。
- JSON、质量报告和单文件 HTML 导出。
- CLI、本地服务、安全边界和自动化回归。

### 3.2 产品化缺口

| 缺口 | 用户影响 | 优先级 |
| --- | --- | --- |
| 缺少安全分享模式 | 导出内容可能包含源码摘录，不适合直接传播 | P0 |
| 缺少结果可信度总结 | 用户难以判断本次分析可不可以用于评审 | P0 |
| 缺少场景、状态与存储模型 | 只能解释局部字段转换，不能表达完整业务闭环 | P0 |
| Java 解析能力有限 | 无法可靠覆盖主要企业项目场景 | P0 |
| 缺少模块与入口引导 | 用户容易导入过大范围并得到噪声结果 | P1 |
| 缺少项目、历史和版本对比 | 分析结果不能长期积累为项目知识 | P1 |
| 缺少人工确认与修订记录 | 业务语义无法形成可追踪的团队共识 | P1 |

## 4. 版本路线

### v0.2：可信交付与安全分享

目标：让一次分析结果可以被正确理解、安全导出并用于内部评审。

#### 交付范围

- 新增分析质量面板：源码事实、静态匹配、推断关系、未知关系和限制项。
- 新增三种导出级别：
  - 完整内部版：包含源码证据。
  - 脱敏评审版：保留文件与证据摘要，不包含代码正文。
  - 业务演示版：只保留流程、状态、字段和已确认说明。
- 导出前展示内容清单与风险确认。
- 增加入口分析摘要，说明当前流程是否适合评审或分享。
- 统一页面中的“事实、推断、模拟、未知”视觉标识。

#### 验收门槛

- 无源码导出包中不出现源码正文、绝对路径、令牌和连接字符串。
- 每个流程节点都能显示其依据类型。
- 未解析连接不能被计入已确认覆盖率。
- 导出包在离线环境中可打开，不访问外部资源。
- 安全回归、Schema 校验和浏览器测试全部通过。

### v0.3：业务场景与草稿箱标杆

进度：`0.3.0-alpha.1` 已完成独立参考模型与通用渲染切片，见[第一阶段报告](09-v03-scenario-lab.md)。两类合成案例展示四类路径、状态、逻辑存储快照及未验证事务边界；尚未接入真实源码、用户确认或安全分享自定义场景，不能视为本节全部完成。

补充进度：`0.3.0-alpha.2` 增加参考路径终点对比与存储显式操作轨迹，见[第二阶段报告](10-v03-path-comparison.md)。它用于核对人工模型的差异，不验证运行等价、幂等或真实事务；未接入源码/用户场景，完整路线任务仍不勾选。

目标：从“代码步骤解释”升级为“业务流程解释”，以草稿箱作为第一个完整标杆案例。

#### 中间模型扩展

- `scenarios`：主路径、拒绝路径、失败路径与恢复路径。
- `states`：状态、迁移条件、终态和非法迁移。
- `stores`：MongoDB、关系库、队列等逻辑存储节点。
- `mutations`：插入、更新、删除、字段 unset 和版本递增。
- `transactionRegions`：已证实事务范围和未确认传播边界。
- `snapshots`：场景步骤前后的数据投影。
- `assumptions`：人工补充但尚未被源码证明的业务说明。

#### 草稿箱标杆场景

1. 创建草稿：`requestKey` 幂等登记、`clientDraftKey` 防重复创建。
2. 更新草稿：`revision` 乐观锁与版本冲突。
3. 自动保存：重复请求、超时和重试结果。
4. 正式提交：草稿冻结、业务提交、Outbox 和最终状态。
5. 故障恢复：写入成功但回执未确认、恢复任务补偿。
6. 生命周期：删除、过期和数据清理。

#### 验收门槛

- 同一通用渲染器可以展示成功、冲突、失败和恢复场景。
- 草稿箱专有文案与表名不能写死在通用页面逻辑中。
- 每个状态变化和数据变化都有源码证据或明确的人工确认标识。
- MongoDB 与关系库之间的非原子窗口不能被画成单一强事务。
- 第二个非草稿案例可以复用相同场景模型和页面组件。

### v0.5：真实 Java 项目分析

目标：让产品能够处理经过范围确认的 Java/Spring 真实模块，而不只依赖有限词法匹配。

#### 交付范围

- 引入完整 Java AST 与符号解析适配层。
- 支持类、接口、实现、重载、泛型和跨文件引用。
- 识别 Spring Controller、Service、Repository 与常见依赖注入线索。
- 对事务注解、代理边界和传播行为保持保守判断。
- 增加“选择模块 → 推荐入口 → 确认范围 → 开始分析”向导。
- 对超出支持范围的反射、动态代理和运行时配置生成可操作诊断。

#### 验收门槛

- 在授权的真实小模块上建立人工参考答案。
- 关键入口、主要调用关系和 DTO 字段无关键误报。
- 多实现或重载存在歧义时不得自动选择一个答案。
- 固定源码和配置下，重复分析生成稳定结果。
- 分析过程不执行目标项目的构建、安装脚本和业务代码。

### v0.8：项目化沉淀

目标：将一次性分析工具升级为可以持续维护的项目知识空间。

#### 交付范围

- 本地项目列表与最近分析记录。
- 分析快照、版本对比和证据陈旧提示。
- 人工确认、说明、批注和修订历史。
- 流程节点与 Git 提交、文件变化之间的影响关联。
- 支持重新分析后保留仍然有效的人工说明。
- 项目级安全设置和默认导出策略。

#### 验收门槛

- 用户可以重新打开历史项目并查看当时的分析快照。
- 源码变化后，系统能指出失效证据和受影响流程。
- 人工修订保留作者、时间、依据和前一版本。
- 删除本地项目时明确说明删除范围，不影响被分析源码。

### v1.0：可交付的代码流程工作台

目标：完成从源码理解、业务解释、证据核对到安全分享的稳定闭环。

#### 发布门槛

- 至少通过一个真实 Java/Spring 模块和一个独立 JS/TS 模块。
- 草稿箱标杆覆盖创建、更新、提交、冲突和恢复流程。
- 关键源码事实证据覆盖率为 100%；未知项全部披露。
- 支持完整内部版、脱敏评审版和业务演示版导出。
- 支持项目历史、快照对比和证据陈旧检查。
- 核心任务在桌面端和窄屏设备上无阻断。
- 安全、模型、CLI、浏览器和离线导出回归全部通过。

## 6. 产品指标

### 6.1 北极星指标

**一次分析中，被用户确认且具备有效证据的关键流程结论数量。**

该指标同时约束产品价值和真实性，避免只追求上传次数、节点数量或页面访问量。

### 6.2 阶段指标

| 维度 | 指标 | v1.0 目标 |
| --- | --- | --- |
| 激活 | 首次用户完成“导入 → 选择入口 → 查看证据 → 导出” | ≥ 70% |
| 效率 | 在小型模块中找到目标入口并生成首个流程 | ≤ 5 分钟 |
| 可信度 | 关键源码事实拥有有效证据 | 100% |
| 透明度 | 未解析、推断和模拟关系获得显式标记 | 100% |
| 泛化 | 不修改渲染器即可支持的独立业务案例 | ≥ 2 个 |
| 安全 | 无源码分享包中的源码正文泄漏 | 0 项 |
| 稳定性 | 核心自动化与浏览器回归 | 100% 通过 |

## 8. 决策原则

后续需求按以下顺序取舍：

1. 安全与事实正确。
2. 业务语义和证据完整。
3. 对不同项目的泛化能力。
4. 用户完成核心任务的效率。
5. 视觉表现和动画效果。

任何新能力都必须同时回答：

- 它解决的是哪个用户任务？
- 结论来自源码、推断、人工确认还是模拟？
- 如何证明没有把未知包装成事实？
- 如何测试并防止回归？
- 导出后是否可能泄漏不应分享的内容？

## 9. 主要风险与应对

| 风险 | 应对 |
| --- | --- |
| Java 动态行为无法静态证明 | 保守保留未知；允许人工确认，不自动补造绑定关系 |
| 场景模型过拟合草稿箱 | 以第二个独立业务案例作为版本门禁 |
| 功能增多导致页面信息过载 | 根据用户任务分层展示，默认只显示当前路径和关键结论 |
| 导出包含敏感源码 | 默认使用脱敏评审版，完整内部版需要主动选择 |
| 用户把动画理解为真实执行 | 持续显示静态/模拟标识，动画时间不表达性能 |
| 大仓库分析范围失控 | 分析前进行模块、入口和文件范围确认 |
| 人工修订掩盖原始事实 | 修订作为独立图层保存，不覆盖解析结果和证据 |

## 10. 首轮启动建议（已按此执行 v0.2）

下一迭代建议直接启动 v0.2，并以“可安全分享的一次分析”为唯一主题：

1. 先定义依据类型、质量摘要和三种导出规格。
2. 用现有 TypeScript 与 Java 示例建立导出安全测试。
3. 完成页面和 CLI 的三类导出。
4. 通过安全、Schema、Node、浏览器和离线回归后发布 v0.2.0。

完成 v0.2 后，再进入草稿箱场景模型，避免在分享边界尚不安全时提前扩大业务数据表达范围。
